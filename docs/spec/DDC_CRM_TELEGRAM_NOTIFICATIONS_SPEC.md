# Уведомления в Telegram — контракт модуля

Документ описывает фактическое поведение кода: какие сообщения бот отправляет сотрудникам, кто и
как ими управляет, и что нужно сделать, чтобы добавить новый тип. Доменный контекст —
[docs/domain/communication.md](../domain/communication.md), поля таблицы — [docs/schema.md](../schema.md).

Это исходящие служебные уведомления для сотрудников, а не канал общения с клиентами. Модуль не
связан с двумя другими интеграциями Telegram: входом через Telegram (OIDC) и Mini App администратора.

## Типы уведомлений

Список типов и значения по умолчанию заданы в коде —
`server/src/modules/communication/telegram/notification-settings.service.ts`
(`TELEGRAM_NOTIFICATION_DEFINITIONS`).

| Ключ | Событие | Группа на странице | Куда уходит | По умолчанию |
|---|---|---|---|---|
| `NEW_STUDENT` | Создан ученик | Ученики и Mollie | Общая группа | выключено |
| `NEW_MOLLIE_CUSTOMER` | Создан клиент Mollie | Ученики и Mollie | Общая группа | выключено |
| `MOLLIE_PAYMENT` | Платёж Mollie: оплата, ошибка, отмена, истечение, возврат, chargeback | Ученики и Mollie | Общая группа | включено |
| `LOGIN_BLOCKED` | Вход заблокирован по лимиту попыток | Безопасность | Общая группа | включено |
| `NEW_DEVICE_AFTER_FAILURES` | Вход с нового устройства после неудачных попыток | Безопасность | Общая группа | включено |
| `ROLE_CHANGED` | Пользователю изменили роль | Безопасность | Общая группа | включено |
| `NEW_EMAIL` | Новое входящее письмо, не спам | Почта | Личный чат администратора | включено |

Получатели задаются окружением:

- **Общая группа** — `TELEGRAM_TOKEN` + `TELEGRAM_CHAT_ID`.
- **Личный чат администратора** — `TELEGRAM_TOKEN` + `TELEGRAM_EMAIL_NOTIFY_CHAT_ID`.

Отдельного чата на каждый тип нет.

## Когда уведомление отправляется

Уведомление уходит, только если выполнены оба условия:

1. В окружении настроен чат получателя этого типа.
2. Переключатель типа включён.

Проверка — `canSendNotification(key)` в `telegram.service.ts`.

Правила, общие для всех типов:

- **Отправка не влияет на основное действие.** Вызовы идут как fire-and-forget: ошибка Telegram
  пишется в лог, а создание ученика, вебхук Mollie или вход продолжаются.
- **Сбой чтения настройки равен значению по умолчанию.** Если строку не удалось прочитать из
  базы, существующие типы отправляются, а два новых — нет.
- **Персональные данные в группу не уходят.** Сообщения о новом ученике и клиенте Mollie содержат
  имя и ссылку в CRM, но не телефон, email, дату рождения или IBAN. Ссылка строится от
  `CLIENT_URL`; если переменная не задана, сообщение уходит без ссылки.

## Откуда вызываются уведомления

| Тип | Место вызова |
|---|---|
| `NEW_STUDENT` | `clients.service.createClient`, после фиксации транзакции. Вызов стоит в сервисе, а не в контроллере, поэтому покрыты все пути создания: форма CRM и Telegram Mini App. |
| `NEW_MOLLIE_CUSTOMER` | `payments.controller` при создании клиента из CRM и `payments.sync.service` при синхронизации с Mollie. |
| `MOLLIE_PAYMENT` | Вебхук Mollie в `payments.controller`. |
| `LOGIN_BLOCKED` | `auth.login-rate-limit.middleware`. |
| `NEW_DEVICE_AFTER_FAILURES` | `auth.controller`, после успешного входа. |
| `ROLE_CHANGED` | `users.controller`. |
| `NEW_EMAIL` | IMAP-синхронизация, `email-imap.service`. |

### Новый ученик

Сообщение содержит имя и фамилию, филиал, источник (`CRM` или `Telegram Mini App`), email
создавшего сотрудника и ссылку на карточку. Автор и источник передаются в `createClient` из
контроллера и в базе не сохраняются.

### Новый клиент Mollie

Сообщение содержит имя плательщика, источник (создан в CRM или пришёл при синхронизации),
признак «привязан к ученику / не привязан» и ссылку на карточку.

Синхронизация объявляет новых клиентов один раз за прогон:

- до трёх новых клиентов — отдельное сообщение на каждого;
- больше трёх — одно сводное сообщение со счётчиком и ссылкой на список.

Порог — константа `MAX_INDIVIDUAL_CUSTOMER_NOTIFICATIONS` в
`new-record-notifications.service.ts`. Клиент, созданный вне полного прогона (платёж от ещё
неизвестного плательщика), объявляется отдельным сообщением.

## Настройки

Таблица `telegram_notification_settings` (модель `TelegramNotificationSetting`) хранит одну строку
на тип: ключ, состояние, кто и когда изменил. Строка появляется только после первого изменения;
пока её нет, действует значение по умолчанию из кода. Миграция создаёт пустую таблицу.

### API

Оба маршрута доступны только роли `ADMIN`.

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/telegram-notifications` | Список всех типов: ключ, название, группа, получатель, состояние, настроен ли чат получателя, кто и когда изменил. |
| `PUT /api/v1/telegram-notifications/:key` | Изменить состояние. Тело — `{ "enabled": boolean }`, лишние поля отклоняются. Неизвестный ключ — `404`, неверное тело — `400`. |

Поле `configured` в ответе показывает, заданы ли в окружении токен и чат получателя. Сами
значения токена и идентификаторов чатов API не возвращает.

### Объявление об изменении

Каждое фактическое изменение переключателя отправляет в общую группу сообщение «Изменены
настройки уведомлений» с названием типа, новым состоянием и email администратора
(`notifyNotificationSettingChanged`). Это сообщение намеренно не имеет собственного
переключателя: уведомления, включая уведомления безопасности, нельзя выключить незаметно для
группы. Повторное сохранение того же значения ничего не отправляет.

Журнала изменений в CRM нет — историю даёт сама группа.

## Страница «Уведомления»

- Адрес `/notifications`, пункт меню в группе «Компания». Пункт виден только администратору.
- Переключатели сгруппированы: «Ученики и Mollie», «Безопасность», «Почта».
- Клик сохраняет состояние сразу. При ошибке сохранения переключатель остаётся в прежнем
  положении, в строке показывается ошибка.
- У каждого типа — описание, отметка «кто и когда изменил» и предупреждение, если чат получателя
  не настроен.
- Не-администратор, открывший адрес напрямую, видит сообщение о недоступности раздела; запрос к
  API не отправляется.

Код страницы — `client/src/pages/NotificationsPage`. Описания типов для интерфейса лежат на
клиенте (`notificationTexts.ts`), названия приходят с сервера.

## Как добавить новый тип уведомления

1. Добавить ключ в `TELEGRAM_NOTIFICATION_KEYS` (`notification-settings.types.ts`).
2. Добавить описание в `TELEGRAM_NOTIFICATION_DEFINITIONS`: название, группа, получатель,
   значение по умолчанию. Новый тип, меняющий привычное поведение группы, должен быть выключен
   по умолчанию.
3. Написать функцию `notify*`, которая первым делом проверяет `canSendNotification(key)`, и
   вызвать её из сервиса-владельца события как fire-and-forget.
4. Добавить описание типа в `notificationTexts.ts` на клиенте.
5. Обновить таблицу типов в этом документе.

Миграция базы не нужна. Новая группа на странице или новый получатель требуют расширения типов
`TelegramNotificationGroup` / `TelegramNotificationRecipient` на сервере и на клиенте.

## Проверки

| Область | Команда |
|---|---|
| Настройки, контроллер, тексты сообщений, проверка переключателя | `npm run test:auth` (из `server/`) |
| Уведомления при синхронизации Mollie | `npm run test:mollie` (из `server/`) |
| Передача автора и источника при создании ученика | `npm run test:ci` (из `server/`) |
| Страница и пункт меню | `npm test` (из `client/`) |
| Переключение, сохранение после перезагрузки, вёрстка на телефоне | `e2e/specs/notifications.spec.ts` |

Отправка в настоящий Telegram автоматическими тестами не покрыта: в тестах HTTP-вызов Bot API
подменён, на E2E-стенде Telegram не настроен.

## Вне рамок модуля

- Управление переключателями из Telegram-бота или Mini App.
- Отдельный чат для каждого типа и персональные подписки сотрудников.
- Кнопка тестовой отправки.
- Уведомления об изменении и удалении учеников.
- Сообщения утверждения черновиков AI-ассистента — это отдельный поток, см.
  [DDC_AI_EMAIL_WORKFLOW.md](DDC_AI_EMAIL_WORKFLOW.md).
