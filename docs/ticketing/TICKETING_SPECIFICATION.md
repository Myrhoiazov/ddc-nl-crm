# DDC Ticketing — спецификация MVP (черновик для ревью)

Статус: черновик по итогам discovery, не утверждён. Основан на `PROJECT_BRIEF.md` v0.1 и фактах из `CURRENT_ARCHITECTURE.md`.
Обозначения: **[Факт]**, **[Предложение]**, **[Неизвестно]**, **[Решение бизнеса]**.

## 1. Цель и границы

Продажа билетов на концерт с выбором конкретных мест через сайт на WordPress; учёт, оплата и администрирование — в существующем DDC CRM. Первое событие — 260 мест; фактическая рассадка по рядам подтверждается площадкой.

### В MVP

- События и сеансы; площадки и версионируемые схемы зала; генератор рядов, категории, заблокированные места.
- Инвентарь и цены на сеанс; гостевая покупка; выбор мест с телефона.
- Атомарный hold нескольких мест со сроком; цена считается на сервере; разовый платёж Mollie; проверяемая обработка webhook.
- Один билет на место, opaque QR, PDF, email; восстановление заказа и повторная отправка.
- В CRM: поиск заказов, ручная блокировка мест, возвраты, отчёт о продажах; мобильный check-in с запретом повторного прохода.
- Встраивание в WordPress, локали, приватность и права доступа.

### Вне MVP (из брифа)

Входные билеты без мест, абонементы, промокоды, кошельки (Apple/Google Wallet), Telegram для покупателей, листы ожидания, обмен мест, мультисайт. Дополнительно предлагается исключить: офлайн check-in, личный кабинет покупателя, выбор «лучших мест» автоматически, несколько валют.

## 2. Роли

| Роль | Кто | Доступ |
|---|---|---|
| Покупатель (гость) | без учётной записи | витрина, свой заказ по opaque-токену |
| Кассир / check-in | сотрудник у входа | только сканирование и поиск билета |
| Менеджер | `MANAGER` | события, заказы, блокировки, повторная отправка, отчёты |
| Администратор | `ADMIN` | всё, включая возвраты, публикацию схем, настройки |

## 3. Пользовательские сценарии и критерии приёмки

### 3.1 Покупатель

| ID | Сценарий | Критерии приёмки |
|---|---|---|
| B1 | Открыть витрину на странице сайта | Видны событие, дата, площадка, карта зала с категориями и ценами; интерфейс на языке страницы (NL/EN/RU/UK) |
| B2 | Выбрать места | Занятые и заблокированные места недоступны; лимит мест на заказ соблюдается; на экране 360 px карта масштабируется и панорамируется, место попадается пальцем; есть альтернатива карте — список мест (доступность) |
| B3 | Удержать места | Нажатие «Продолжить» удерживает **все** выбранные места или ни одного; при конфликте показано, какие места заняты; виден таймер |
| B4 | Оформить | Имя, email, согласие с условиями; сумма рассчитана сервером и совпадает с показанной; переход на оплату Mollie в окне верхнего уровня |
| B5 | Вернуться после оплаты | Страница результата показывает реальный статус с сервера (не из параметров URL); пока платёж обрабатывается — состояние ожидания с автообновлением |
| B6 | Получить билеты | Email с PDF, по одному билету на место; на странице заказа билеты доступны и без email |
| B7 | Восстановить заказ | По email + номеру заказа приходит новая ссылка; ответ формы одинаков для существующих и несуществующих заказов |
| B8 | Отказаться | Отмена до оплаты освобождает места сразу |

### 3.2 Администрирование

| ID | Сценарий | Критерии приёмки |
|---|---|---|
| A1 | Создать площадку и схему зала | Генератор рядов (количество рядов, мест, нумерация, направление); перемещение и удаление мест; назначение категорий; блокировка мест по умолчанию |
| A2 | Опубликовать схему | Опубликованная версия не редактируется; изменение создаёт новую версию-черновик |
| A3 | Создать событие и сеанс | Сеанс привязан к опубликованной версии схемы; цены по категориям; окно продаж; публикация генерирует инвентарь |
| A4 | Управлять местами сеанса | Ручная блокировка/разблокировка с причиной; проданные и удерживаемые места блокировать нельзя |
| A5 | Найти заказ | Поиск по номеру, email, имени, коду билета; карточка заказа с историей событий |
| A6 | Повторно отправить билеты | Новое письмо на email заказа; факт записан в журнал |
| A7 | Сделать возврат | Полный или по отдельным местам; обязательная причина; билеты аннулируются только после подтверждения возврата Mollie |
| A8 | Отчёт о продажах | По сеансу: продано/удержано/свободно/заблокировано, выручка по категориям, возвраты; экспорт CSV (прецедент — `createCsv`, `payments.utils.service.ts:45-47`) |
| A9 | Разобрать проблемные заказы | Экран «Требуют внимания» со статусом Mollie и действиями |
| A10 | Отменить сеанс | Продажи останавливаются, формируется очередь возвратов |

### 3.3 Check-in

| ID | Сценарий | Критерии приёмки |
|---|---|---|
| C1 | Сканировать QR с телефона сотрудника | Ответ < 1 с при нормальной сети; крупный однозначный результат: «Проход разрешён» / «Уже использован (время, кем)» / «Недействителен» / «Другой сеанс» |
| C2 | Два сканера сканируют один билет одновременно | Ровно один получает «разрешён» |
| C3 | Ручной ввод кода | Работает при неисправной камере |
| C4 | Счётчик | Видно «прошло N из M» по сеансу |
| C5 | Отмена прохода | Только менеджер/админ, с причиной |

## 4. Нефункциональные требования (измеримые)

| Требование | Цель |
|---|---|
| Отсутствие двойной продажи | 0 случаев в нагрузочном тесте: 500 параллельных попыток на 260 мест, пересекающиеся наборы |
| Атомарность hold | 0 частичных удержаний в том же тесте |
| Время ответа hold | p95 < 500 мс при 50 одновременных покупателях |
| Check-in | p95 < 300 мс на сервере; 0 двойных проходов при 20 параллельных сканах одного билета |
| Восстановление без webhook | оплаченный заказ получает билеты ≤ 10 мин без единого webhook |
| Доставка email | ≥ 3 автоматических повтора; заказ доступен без email |
| Доступность | управление с клавиатуры, ARIA-метки мест, не только цвет как носитель статуса, списочная альтернатива карте |
| Размер витрины | отдельный бандл, цель ≤ 150 КБ gzip (подлежит уточнению) |

## 5. Встраивание в WordPress

**[Факт]** локальная копия темы осмотрена 2026-11-27 (`CURRENT_ARCHITECTURE.md` §7): WordPress 6.8.3, Polylang, W3 Total Cache. Прод-настройки веб-сервера и кэша **не проверены**.

| Критерий | iframe (приложение на домене CRM/поддомене билетов) | JS-виджет (скрипт в странице WordPress) |
|---|---|---|
| Изоляция стилей и скриптов | Полная | Нужен Shadow DOM; конфликты с темой и плагинами возможны |
| CORS | Не нужен: API того же origin, что и приложение | Нужен: сейчас разрешён только `CLIENT_URL` (`app.ts:25-28`) |
| CSP сайта | Нужен `frame-src` на наш домен | Нужны `script-src` и `connect-src` на наш домен |
| Оптимизаторы/кэш WordPress | Не затрагивают | Могут минифицировать, откладывать или ломать скрипт |
| Высота и прокрутка | Нужен `postMessage` для авто-высоты | Естественная |
| Мобильный зум карты | Жесты внутри iframe; нужен собственный pinch-zoom, чтобы не конфликтовать с прокруткой страницы | То же, но проще координировать с прокруткой |
| Возврат после оплаты | Mollie нельзя открывать во фрейме → навигация верхнего уровня; возврат на страницу сайта с параметром заказа, плагин передаёт его в iframe | Параметр читается напрямую |
| Хранилище в браузере | Сторонний контекст: хранилище изолировано, Safari может его очищать → состояние hold держать в URL/памяти и уметь восстановить с сервера | Обычное first-party |
| SEO | Содержимое не индексируется | Индексируется при серверной разметке |
| Обновления | Деплой нашего приложения, плагин не трогаем | То же, но версия скрипта кэшируется сайтом |
| Безопасность | Компрометация плагина сайта не даёт доступа к DOM витрины | Любой скрипт сайта видит DOM и данные формы |

**Рекомендация [Предложение]:** iframe + минимальный плагин с шорткодом (`[ddc_tickets event="slug" lang="nl"]`), который выводит iframe, скрипт авто-высоты и пробрасывает параметр возврата. Запасной вариант, не зависящий от плагина, — прямая ссылка на полноэкранную страницу витрины.

Сопутствующие изменения на нашей стороне:
- исключение публичного префикса из CSRF (`auth.csrf.middleware.ts:19-36`) — собственная защита через токены, rate-limit, Turnstile;
- заголовок `frame-ancestors` для витрины со списком разрешённых сайтов — задаётся на frontend-nginx (`docker/client/nginx/default.conf` сейчас заголовков безопасности не выставляет);
- **[Решение бизнеса]** домен витрины. Сейчас прод-шаблон nginx обслуживает технический домен (`deploy/nginx/ddc-nl.conf:23`); покупателю в адресной строке при оплате и в письмах лучше видеть домен бренда — рекомендуется поддомен вида `tickets.<домен сайта>`.

**Локали.** В CRM только `en`/`ru` (`client/public/locales/`), нидерландской нет. Витрина получает собственные словари NL/EN/RU/UK — на сайте четыре языка через Polylang (`CURRENT_ARCHITECTURE.md` §7); язык задаётся параметром шорткода. Язык страницы оплаты Mollie — через существующее сопоставление (`payments.utils.service.ts:7-15`; для RU Mollie локали не имеет).

**[Факт]** ролей три (`ADMIN`, `MANAGER`, `DOCTOR` — `user.prisma:1-5`), роли check-in нет; Mollie- и invoice-маршруты роль не проверяют вовсе.

| Вариант роли check-in | Плюсы | Минусы |
|---|---|---|
| **Новое значение enum `CHECKIN`** | Явно, проверяется существующим `requireRole` (`auth.middleware.ts:53-63`) | Миграция enum; нужно убедиться, что новая роль не получает доступ к маршрутам «только `isAuthenticated`» — таких большинство (Mollie, счета, клиенты) |
| Переиспользовать `DOCTOR` | Без миграции | Семантически неверно; та же проблема с открытыми маршрутами |
| Отдельный код/ссылка сканера на сеанс без учётной записи | Просто для волонтёров | Новый механизм аутентификации, слабее аудит |

Рекомендуется первый вариант **вместе с** аудитом существующих маршрутов: пользователь с ролью `CHECKIN` сегодня смог бы читать клиентов и платежи. Это отдельная задача плана и предварительное условие.

## 7. Предлагаемые API-контракты (черновик)

Публичные (без сессии, исключены из CSRF, rate-limit по IP и токену):

| Метод и путь | Назначение |
|---|---|
| `GET /api/v1/ticketing/public/events/:slug` | событие и его сеансы |
| `GET /api/v1/ticketing/public/sessions/:id/seat-map` | геометрия, категории, цены (кэшируемо) |
| `GET /api/v1/ticketing/public/sessions/:id/availability` | только статусы мест (часто, легко) |
| `POST /api/v1/ticketing/public/sessions/:id/holds` | `{seatIds[], requestKey}` → `201 {holdToken, expiresAt}` / `409 {unavailableSeatIds}` |
| `DELETE /api/v1/ticketing/public/holds/current` | освободить (токен в заголовке) |
| `POST /api/v1/ticketing/public/orders` | `{buyer, locale, acceptedTermsVersion}` + токен hold → `{orderToken, checkoutUrl}` |
| `GET /api/v1/ticketing/public/orders/current` | статус заказа и билеты (токен в заголовке) |
| `GET /api/v1/ticketing/public/orders/current/tickets.pdf` | PDF |
| `POST /api/v1/ticketing/public/orders/recover` | `{email, orderNumber, captcha}` → всегда `202` |
| `POST /api/v1/ticketing/webhooks/mollie` | webhook, исключён из CSRF |

Административные (сессия + CSRF + роль): `/api/v1/ticketing/admin/venues`, `/seat-maps` (+ `/:id/publish`, `/:id/clone`), `/events`, `/sessions` (+ `/:id/publish`, `/:id/seats/block`), `/orders` (+ `/:id/resend`, `/:id/refunds`, `/:id/resolve`), `/reports/sessions/:id` (+ `.csv`), `/check-in/scan`, `/check-in/sessions/:id/stats`.

Цены, суммы и доступность клиент **никогда** не передаёт — только идентификаторы мест.

## 8. Навигация в CRM

Новая группа в боковом меню «Билеты» (`getSidebarItems.ts`):

- События — список, карточка события с сеансами.
- Залы — площадки и версии схем, SVG-редактор.
- Заказы — поиск, карточка, возвраты.
- Требуют внимания — счётчик-бейдж.
- Отчёты.
- Check-in — мобильная страница сканера.

Новые слайсы по FSD: `pages/Ticketing*`, `features/ticketSeatMapEditor`, `entities/TicketEvent|TicketOrder|TicketSeatMap`. Редактор — SVG; для панорамирования и масштабирования можно использовать уже установленный `@use-gesture/react`. Витрина — **отдельный** пакет/бандл по образцу `client/telegram-mini-app/` (свой вход, свои словари, без Redux и остального CRM), чтобы не тянуть административный код покупателю; общие с редактором примитивы отрисовки карты выносятся в разделяемый модуль.

## 9. Вопросы, требующие решения бизнеса

Юридических выводов этот документ не делает.

### Деньги и налоги
1. Цены по категориям; включён ли НДС; ставка НДС для данного типа события и эмитента — подтверждает бухгалтер.
2. Сервисный сбор: есть ли, фиксированный или процент, кто несёт комиссию Mollie.
3. Какой документ получает покупатель: достаточно ли билета и письма-подтверждения, или нужен счёт с НДС. **[Факт]** существующая модель `Invoice` не содержит полей НДС (`invoice.prisma:29-86`).
4. Эмитент: какое юрлицо/бренд (`BusinessBrand`) и какой профиль Mollie.
5. Разрешённые методы оплаты.

### Возвраты и права потребителей
6. Политика возвратов по инициативе покупателя и сроки; действует ли право на отказ для билетов на датированные мероприятия — подтверждает юрист.
7. Возврат сервисного сбора при отмене события.
8. Поведение при chargeback.
9. Автоматический или ручной возврат при поздней оплате на уже занятые места.

### Приватность
10. Перечень собираемых данных (минимум: имя, email; нужен ли телефон).
11. Срок хранения данных заказов и процедура удаления/анонимизации; обновление политики конфиденциальности сайта.
12. Тексты условий продажи и версии согласий.
13. Кто из персонала видит данные покупателей.

### Операции
14. Подтверждённая площадкой схема: ряды, нумерация, места для людей с ограниченной мобильностью, изъятые места.
15. Число сеансов, даты, окна продаж, лимит мест на заказ.
16. Кто и с каких устройств проводит check-in; качество сети на площадке.
17. Кто дежурит в день события и разбирает проблемные заказы.
18. Домен витрины и адрес отправителя писем (нужны SPF/DKIM для отправителя).
19. Кто администрирует WordPress и может установить плагин.

### Технические неизвестные (проверить до утверждения спецификации)
20. Режим Mollie в проде (OAuth/API-ключ), доступность тестового режима.
21. Сроки жизни платежа по методам, поддержка idempotency-ключей в SDK.
22. Рабочий канал исходящей почты в проде (`SMTP_*` против `EmailAccount`).
23. Наличие бэкапов и мониторинга на VPS.
24. Параметры WordPress: версия, тема, плагины кэша и безопасности, CSP.
